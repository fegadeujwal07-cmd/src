Why drop_corridor.cpp exists

Your code review checklist (C++ Engineering Code Review & Developer Checklist.xlsx) caps functions at 40 lines and files at 1,000 lines. The first version of the corridor code broke both rules. The corridor search alone was about 150 lines, and it sat inside execution_full_control.cpp, which is already over 10,000 lines.

So the corridor logic moved into its own small module:

  • drop_corridor.hpp / .cpp answer the pure questions. Which lanes are free and which are blocked? Is this RMF path on the corridor? Has the robot started travelling? There is no ROS code here, so it can be tested on its own. It was tested against your real 0.yaml and all checks passed.
  • execution_full_control.cpp keeps only short glue that calls the module at the right moments: at pickup completion, when a PathRequest arrives, every 200 ms, and at drop completion. It also publishes on /robot_lane_requests.

Behaviour is the same as before the split. Only the structure changed so the code follows the checklist: every function is 32 lines or fewer, lines are at most 80 columns, the header is down to 983 lines, and the package builds as C++20.

155+ std::queue<std::size_t> frontier;
156+ frontier.push(from);
